## Purpose

Build the database textbook platform in a practical sequence that supports the course now, while preparing for paid access later.

- **Immediate goal**: Students can read assigned chapters and labs when the course starts.
- **Next operational goal**: Students can create accounts, log in, pay via Stripe Checkout, and receive protected access through Supabase.
- **Long-term goal**: A stable textbook platform with protected access, student learning features, and a controlled publishing workflow.

## Phase 3 — Paid Access Pilot (Supabase + Stripe) ⏳ NEXT

**Start after**: Free reader is stable with domain AND Phase 2 build passes. May partially overlap with Phase 2 if resources allow, but free reader stability comes first.

**Minimum for testing**: ch01 preview (free) + ch02 locked (paid). All 17 chapters NOT needed.

### Technology
Next.js (App Router) · TypeScript · Supabase Auth (`@supabase/ssr`) · Supabase Postgres + RLS · Stripe Checkout (mode: `payment`) · Stripe Webhooks · Vercel

### App Location
Preferred: `books/database-book/platform-pilots/claude/` (if functional). Deploy as separate Vercel project: `data-textbook-pilot`.

### Immediate Strategy: Roster-Based Free Access First

Supabase login + roster-based access is already live in the v1.1 reader. Use this as the foundation. Stripe is the next monetization layer — not an emergency.

**For Week 1-2**: eligible students register with their university email, get roster-verified access through Supabase, and can read Ch01-Ch04 (free) and Ch05+ (authenticated). Set a free access expiration (e.g., June 30) so there's a natural transition point.

**Stripe comes after** urgent book content work is done. The registration/access system is already enough to let students start.

```
Now:  Supabase login + roster access = live
      Book/Labs gated = live
      Stripe = next phase
```

**When to implement Stripe**:
1. Finish first-week chapters/labs
2. Upload full roster
3. Confirm students can register
4. Add a "Payment coming soon / trial access active" message
5. Implement Stripe Checkout + webhook
6. Test payment in Stripe test mode
7. Turn on live payment

### Stripe Flow (When Ready)

```
Student logs in
  ↓
Student is recognized by Supabase
  ↓
Student clicks "Pay for access"
  ↓
Stripe Checkout opens
  ↓
Payment succeeds
  ↓
Stripe webhook tells Supabase
  ↓
Supabase creates access_grants row:
  grant_type = paid
  expires_at = September 2
  ↓
Student keeps access
```

### Payment Decision (Locked)
- **One-time payment**, not subscription
- Product key: `database-book`
- Access can expire at course end via `expires_at` if desired
- Stripe test mode only until full flow is proven
- Do NOT use simple Stripe Payment Links as the main system (requires manual access grants)
- Use Stripe Checkout Sessions + webhooks for automated fulfillment

### Supabase Tables (4 core)

| Table                     | Purpose                                                        |
| ------------------------- | -------------------------------------------------------------- |
| `profiles`                | User display/profile info                                      |
| `access_grants`           | Who can read the protected book (central access-control table) |
| `purchases`               | Stripe payment audit log                                       |
| `processed_stripe_events` | Webhook idempotency / duplicate protection                     |

### Access Logic

- `ch01` → `preview: true` → free for everyone
- `ch02+` → `preview: false` → requires active `access_grant`
- Access active if: logged in AND `access_grant` EXISTS AND `product_key = 'database-book'` AND `status = 'active'` AND `starts_at <= now` AND (`expires_at IS NULL OR expires_at > now`)

### Hard Rules
- **Never unlock access from the browser success page.** Webhook only.
- Server-side route protection must use validated Supabase claims, not `getSession()` alone.
- Service-role key must never reach the browser bundle.
- RLS must be enabled on all public-schema tables.

### Implementation Milestones

**Milestone 1 — Supabase Auth Foundation**
- Supabase project exists, Auth configured
- Signup, login, logout work; account page shows authenticated user
- `profiles` table exists, RLS protects it
- Protected routes use validated claims

**Milestone 2 — Access Model**
- `access_grants`, `purchases`, `processed_stripe_events` tables exist
- RLS enabled on all public tables
- Users read only own rows; service role writes purchases/access_grants
- Ch01 is public, Ch02 is locked unless `access_grant` exists

**Milestone 3 — Stripe Test Product**
- Create Stripe test product ("Database Book — Full Access") in test mode
- Create one-time price, copy `price_XXXX` into `STRIPE_PRICE_ID`

**Milestone 4 — Checkout Endpoint**
- Build `/api/checkout` — requires signed-in user, creates Checkout Session server-side
- Include metadata: `user_id`, `product_key=database-book`
- Redirect to Stripe-hosted Checkout

**Milestone 5 — Webhook Unlock**
- Install Stripe CLI
- Build `/api/stripe/webhook` — verify signature, handle `checkout.session.completed`
- Use `processed_stripe_events` for idempotency
- Insert purchase row + upsert access_grant row

**Milestone 6 — Local End-to-End Test**
- Full flow: logged-out → ch01 works → ch02 blocked → sign up → ch02 still blocked → pay (card `4242 4242 4242 4242`) → webhook fires → ch02 unlocks → duplicate webhook ignored → refresh preserves access

**Milestone 7 — Deploy v2A Test App**
- Deploy to Vercel (separate project: `data-textbook-pilot`)
- Add all env vars, configure Stripe webhook URL
- Test full flow in deployed environment with Stripe test mode

## Key Conventions

### Metadata Comment
Match existing repo convention — single-line HTML comment at top of imported files:
```html
<!-- metadata: date="YYYY-MM-DD" -->
```
Do NOT introduce YAML frontmatter or multi-line `<!-- source:` blocks. Record detailed provenance in `source-import-manifest.csv`.

### `index.md` Rule
- `index.md` is the chapter landing/navigation file — NOT one of the five standard Drive-imported sections
- Do NOT overwrite or regenerate without explicit approval
- Validate for: title match, description freshness, links to stable files, lab link status, repo-only variants

### Lab Answer Rule
- Never expose answer files at lab root level
- Allowed: `files/source/labs/lab-NN-slug/instructor/`
- Embedded answer keys in `review-questions.md` and `rat.md` are KEPT by decision

### Classification Rules (for Phase 2+)

| Classification  | Meaning                                                 | Action                                |
| --------------- | ------------------------------------------------------- | ------------------------------------- |
| **Current**     | Repo matches latest Drive source                        | Do nothing                            |
| **Drive newer** | Drive has later date, repo not independently edited     | Import after approval                 |
| **Repo newer**  | Repo has edits after last import, appears more polished | Do NOT overwrite; flag for review     |
| **Conflict**    | Both changed since last import                          | Do NOT overwrite; manual merge needed |
| **Missing**     | Repo file missing, Drive source exists                  | Import after approval                 |
| **Ambiguous**   | Multiple possible Drive files or unclear date           | Do NOT import; ask for clarification  |
